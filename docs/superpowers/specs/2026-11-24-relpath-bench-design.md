# relpath-bench 설계

작업 이름은 `relpath-bench`다 (PyPI, GitHub 모두 비어 있음, 2026-11-24 확인). 바꿀 수 있다.

## 1. 목적

지식 그래프에서 질문에 필요한 관계 경로를 찾는 알고리즘(PathRAG, Personalized PageRank, PCST 등)을
**같은 그래프, 같은 시작 엔티티, 같은 예산**에서 돌려 비교하는 공개 레포다.
"내 그래프에는 어떤 탐색 방식이 맞는가"를 판단하려는 사람이 명령 하나로 결과표를 재현하고,
자기 알고리즘을 파일 하나로 추가해 같은 표에 올릴 수 있어야 한다.

## 2. 목표, 비목표, 반목표

**목표**
- 알고리즘 여러 개를 공통 인터페이스로 구현하고 같은 조건에서 비교한다
- 검색 단계만 평가한다. API 키 없이, LLM 호출 없이, deterministic하게 돌아간다
- `relpath-bench run` 한 번으로 데이터 다운로드, 전 알고리즘 실행, 결과표 생성까지 끝난다
- README 결과표는 생성기가 채운다. 손으로 고치지 않는다

**비목표**
- LLM 답변 생성과 최종 정답률 평가 (나중에 선택 기능으로 붙일 수 있게 인터페이스만 열어 둔다)
- 텍스트에서 그래프를 만드는 색인 단계
- GNN 학습이 필요한 방법 (G-Retriever의 학습 부분, RoG의 계획 생성 등)

**반목표 (동작해도 실패로 본다)**
- 특정 회사나 조직의 데이터, 스키마, 코드, 이름, 측정값이 레포, 커밋, 이슈 어디에든 들어가는 것
- 결과가 명령 하나로 재현되지 않는 것
- 하이퍼파라미터를 test split에서 고르는 것 (validation split에서만 고른다)
- 원본 PathRAG 코드를 가져오는 것. 원본 레포 `BUPT-GAMMA/PathRAG`는 라이선스가 없다. 논문만 보고 새로 구현한다

## 3. 제약

- Python 3.11 이상, 라이선스 Apache-2.0
- 그래프 코어는 자체 인접 리스트(정수 id, 관계 id)로 만든다. 알고리즘 성능 차이에 그래프 라이브러리 차이가 섞이지 않게 하기 위해서다. 수치 계산은 numpy, scipy 희소 행렬을 쓴다
- 테스트는 pytest, 커버리지 80% 이상. CI는 작은 고정 그래프(수십 노드)로 돌고 데이터셋 다운로드를 하지 않는다
- 커밋 작성자는 개인 계정(`workdd`)

## 4. 접근 방식 (검토한 것)

| 방식 | 내용 | 판단 |
|---|---|---|
| **라이브러리 + 벤치마크 하네스** | 공통 인터페이스, 명령 하나로 전 알고리즘 실행, 결과표 생성 | **채택.** 같은 조건을 코드로 강제할 수 있다 |
| 노트북 중심 | 알고리즘마다 노트북 | 조건이 노트북마다 달라져 비교가 공정하지 않다 |

평가 방식도 세 가지를 검토했다: 검색만 평가, 최종 답까지 평가, 둘 다. **검색만 평가**로 정했다.

## 5. 정한 것

### 5.1 공통 인터페이스

```
Graph            정수 id 인접 리스트. 노드 이름, 관계 이름 사전 포함. 방향 엣지와 역방향 조회 모두 지원
Query            question(문자열), seeds(시작 엔티티 id 목록), answers(정답 엔티티 id 집합), hops(데이터셋이 주면)
Retriever        retrieve(graph, query, budget) -> list[ScoredPath]
ScoredPath       nodes, relations, score
```

- 시작 엔티티는 데이터셋이 주는 topic entity를 그대로 쓴다. 엔티티 링킹과 키워드 추출은 하지 않는다
- **역방향 이동**: 그래프를 만들 때 트리플마다 역관계 `r^-1`을 별도 관계 id로 추가한다. 모든 알고리즘은 정방향과 역관계를 똑같이 지난다. 역관계 이름은 `inverse of <r>`로 만들어 질문 유사도 계산에도 쓴다. 문맥 크기를 셀 때 `(h, r, t)`와 `(t, r^-1, h)`는 트리플 하나로 센다
- **시작 엔티티가 여럿일 때**: 알고리즘마다 시작점 집합을 한 번에 받는다 (PPR은 균등 personalization, BFS와 beam은 모든 시작점에서 동시에 확장)
- 알고리즘은 두 부류로 나뉜다
  - **구조만 보는 방식**: 질문 문장을 보지 않는다
  - **질문을 보는 방식**: 질문과 관계 이름의 유사도를 쓴다. 로컬 문장 임베딩 모델 하나(선택 의존성)로 계산하고 결과를 캐시한다

### 5.2 알고리즘 (첫 판)

| 알고리즘 | 부류 | 근거 논문 | 이 레포에서의 형태 |
|---|---|---|---|
| k-hop BFS | 구조 | 기준선 | 시작점에서 k홉까지 경로 나열. 짧은 경로 우선 |
| Personalized PageRank | 구조 | HippoRAG, arXiv:2405.14831 | 시작점으로 PPR, 상위 노드까지 최단 경로 |
| PathRAG flow 가지치기 | 구조 | PathRAG, arXiv:2502.14902 | 감쇠율과 임계값으로 자원 전파, 경로 점수는 경로 위 자원 평균 |
| PCST | 질문 | G-Retriever, arXiv:2402.07630 | 질문 유사도로 노드, 엣지 상금 부여 후 PCST 부분 그래프에서 경로 추출. 학습 부분 제외 |
| 관계 beam 탐색 | 질문 | Think-on-Graph, arXiv:2307.07697 | 홉마다 LLM 대신 임베딩 유사도로 관계 상위 b개 선택 |

- PathRAG 원 논문은 텍스트에서 만든 그래프에서 **검색된 노드 쌍 사이의 경로**를 찾는다. KGQA는 시작 엔티티가 하나인 경우가 많으므로, 시작점에서 자원이 많이 남은 노드까지의 경로로 바꾼다. 이 변형을 README에 밝힌다
- 각 알고리즘 파일 머리에 논문, 원 논문과 다른 점, 하이퍼파라미터 기본값과 그 출처를 적는다

### 5.4 평가

- **같은 예산 비교**가 원칙이다. 예산은 두 가지로 보고한다
  - 주 표: 반환 경로 수 k ∈ {1, 5, 10, 20}
  - 보조 그림: 문맥 크기(트리플 수) 대 recall 곡선. 긴 경로를 내는 방식이 같은 k에서 유리해지는 효과를 이 그림으로 드러낸다
- 공통 제한: 경로 길이 최대 3홉, 문항당 확장 노드 상한 1만 개. 상한에 걸린 문항 수를 표에 함께 싣는다
- 최대 경로 길이를 3홉으로 두는 이유: MetaQA 질문은 최대 3홉이고, WebQSP test는 정답이 있는 1,557문항 중 2홉, 3홉, 4홉 안에서 정답에 도달하는 문항이 모두 1,552개로 같다 (`harness.reachable`에 `max_hops` 2, 3, 4를 준 측정). MetaQA validation 표본(홉별 30문항, 시드 0)에서 bfs, ppr, pathrag를 측정하면 4홉과 확장 노드 1만 개 상한에서 bfs와 ppr은 33/90 문항이 상한에 걸리고 3홉에서는 0문항이다. hit@10은 두 설정에서 같다 (bfs 55, ppr 61, pathrag 49, 90문항 기준)
- 동점 처리: 점수 내림차순, 경로 길이 오름차순, 노드 id 열 사전순. 이 규칙은 하네스가 강제한다 (알고리즘이 정하지 않는다)
- 지표 (정답 판정은 **경로의 끝 노드만** 본다. 중간 노드에 정답이 지나가도 맞힌 것으로 치지 않는다)
  - hit@k: 상위 k 경로의 끝 노드에 정답이 하나라도 있는 문항 비율
  - recall@k: 정답 엔티티 중 상위 k 경로의 끝 노드에 나타난 비율
  - 문맥 크기: 상위 k 경로에 들어간 서로 다른 트리플 수 (LLM에 넣을 양의 근사)
  - 지연 시간: 문항당 p50, p95 (그래프 로딩 제외)
- MetaQA는 홉 수별, WebQSP는 전체로 표를 만든다
- **도달 불가 정답 (WebQSP)**: 이름을 부분 그래프 노드에 정확히 일치시켜 id로 바꾼다. 정답이 부분 그래프에서 시작점으로부터 3홉 안에 없는 문항은 따로 센다. 표에는 전체 문항 기준과 도달 가능 문항 기준을 둘 다 싣고, 도달 가능 비율(모든 알고리즘의 상한)을 함께 적는다
- **실행 규모**: `run` 기본값은 홉별 고정 시드 1,000문항 표본 (노트북에서 빠르게 확인용). `run --full`은 test 전체. README 표는 `--full` 결과로만 만든다. 문항 단위 결과를 jsonl에 바로 쓰고, 다시 실행하면 이미 끝난 문항은 건너뛴다. 병렬은 문항 단위 프로세스 풀
- **질문을 보는 방식의 의존성**: `pip install relpath-bench[embed]`로 설치한다. 없으면 `run`이 해당 알고리즘을 건너뛰고 건너뛴 사실을 출력한다. README 표 생성은 전 알고리즘 결과가 있어야 진행한다. CI는 임베딩 대신 고정 벡터를 주입해 테스트한다
- 결과는 `results/<dataset>/<algorithm>.jsonl`(문항별)과 요약 표로 남기고, 생성기가 README 표를 갱신한다

### 5.5 저장소 로더와 속도 벤치마크 (두 번째 단계)

- 코어는 `(head, relation, tail)` 목록만 받는다. 로더가 이것을 만든다
- 첫 판 로더: TSV, parquet
- 두 번째 단계 로더: Postgres 엣지 테이블, Apache AGE(라벨 테이블을 SQL로 일괄 조회), Neo4j
- 이번 계획은 1단계만 다룬다. 로더 인터페이스는 `load() -> Iterable[(head, relation, tail)]` 하나로 열어 둔다
- 두 번째 단계에서 docker-compose로 공개 데이터셋(MetaQA)을 AGE와 Neo4j에 적재하고, "DB에서 가변 길이 경로 질의" 대 "일괄 로딩 후 메모리 순회"의 시간을 잰다. 이 값만 README 속도 표에 쓴다

### 5.6 레포 구성

```
relpath_bench/
  graph.py            인접 리스트 코어
  retrievers/         알고리즘 하나당 파일 하나, 등록은 데코레이터
  datasets/           metaqa.py, webqsp.py (다운로드 + Query 생성)
  loaders/            tsv, parquet (2단계: postgres, age, neo4j)
  metrics.py
  cli.py              relpath-bench run / report / list
scripts/render_readme.py   결과 요약 → README 표
tests/                고정 소형 그래프로 알고리즘별 정답 경로 검증
```

## 6. 만드는 사람에게 맡기는 것

- 알고리즘별 하이퍼파라미터 기본값 (논문 값에서 시작, validation split으로 조정)
- 임베딩 모델 선택 (작고 CPU에서 deterministic한 것)
- PCST 구현 의존성 (`pcst_fast` 등)
- MetaQA Google Drive 다운로드 방식 (자동이 깨지면 수동 경로 지정으로 대체)
- 진행 표시, 로그 형식
